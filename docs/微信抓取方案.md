# 微信聊天记录抓取 · 方案

> 定位：这是**施工图**，不是代码。写清楚"抓什么、怎么抓、怎么验、什么时候放弃"。
> 参考实现：https://github.com/binger1210/wechat_capture_tool_BINGER （MIT）
> 目标项目：mail-agent（TypeScript，macOS，零第三方依赖优先）

---

## 〇、先纠正一个说法：参考仓库不抓数据库

那个仓库**没有碰微信的本地加密数据库**。它走的是另一条路：

```
模拟鼠标拖选聊天区 → 点「复制」→ 读系统剪贴板 → 滚动 → 重复
```

作者的核心理由（README 原话）：破解本地加密文件"极易因微信更新而失效，还存在隐私泄露风险"，
所以宁可**通过官方客户端拿已解密的数据**。

**这对我们是好消息** —— 不碰密钥、不碰 WCDB、不碰内存注入，
就不会踩"微信一升级就失效"和"解密工具泄露隐私"这两个坑。

**但它的实现是 Windows 专用**（ctypes WinDLL 监听热键、坐标按 1080P 微信全屏写死），
我们要在 macOS 上重做，核心要移植的是**思路**不是代码。

---

## 一、目标与边界

### 要做的
- 把微信 PC/macOS 客户端里某个会话的聊天记录，**结构化**抓出来（发送者 / 时间 / 内容）
- 输出能直接进我们的**知识库**（kb/），和邮件一起被检索、被问答
- 支持**增量**：只抓新增的，不重复
- 全程本地、不联网、**原始内容不落盘**（沿用邮件那边的要求）

### 不做的（明确划界）
- ❌ 不破解本地数据库（WCDB/SQLCipher）、不注入进程、不提取密钥
- ❌ 不做全微信批量（一个会话一个会话来）
- ❌ 不发送任何消息、不自动回复（那是第⑨步 agent 的事，且要审批流）

## 二、三条技术路线对比

| 路线 | 做法 | 稳定性 | 隐私 | 跨平台 | 评价 |
|---|---|---|---|---|---|
| **A 剪贴板拖选**（参考仓库做法） | 模拟鼠标拖选 → 点复制 → 读剪贴板 | ⭐⭐⭐ 不依赖微信内部结构，微信改版也不太会坏 | 好（数据只经剪贴板） | Windows ✅ / macOS 需重做 | **主路线** |
| **B AppleScript 读 AX 树** | 直接读微信窗口的无障碍元素文本 | ⭐⭐ 依赖微信的 AX 支持，版本变化可能失灵 | 更好（不碰剪贴板） | macOS 原生 | 备选/加速器 |
| **C 解密本地 WCDB** | 从内存拿密钥 → 解 SQLite | ⭐ 微信一升级就废 | 差（工具本身有泄露风险） | 难 | ❌ 不做 |

### 决策：**A 为主，B 做增强**
- A 是被验证过的、和微信内部结构解耦的路子 —— 微信改 UI 只会让坐标偏移，不会让数据抓不到
- B 在 macOS 上更优雅，但微信的 AX 支持不稳定，**只作为"能直读就直读"的加速路径**
- C 直接排除

## 三、macOS 上的关键改造（参考仓库不能直接用的地方）

参考仓库的问题，逐条对应解法：

| 参考仓库的坑 | macOS 上的解法 |
|---|---|
| 坐标写死（1080P 微信全屏） | **不写死坐标**：先用 AppleScript 把微信窗口激活并**标准化 bounds**（比如固定 1200×800 居中），坐标全部相对窗口算 → 分辨率无关 |
| `ctypes.WinDLL("user32")` 监听 Ctrl+Backspace | macOS 用 `Carbon RegisterEventHotKey` 或 `pynput`/`keyboard` 监听；或更简单：**监听控制台输入 + 抓取过程中的信号量** |
| `pyautogui` 需要辅助功能权限 | macOS 要给终端/程序授「辅助功能」权限；**权限检测要在启动时做，缺权限就明确报错**（不要静默失败） |
| 微信窗口被遮挡就抓不到 | 抓取前用 AppleScript `activate` + 把窗口置顶（`System Events`）；**抓取期间禁止用户操作鼠标**（提示 + 倒计时） |

## 四、模块落位

```
src/
├── capture/
│   ├── wechat/
│   │   ├── window.ts       ③ 窗口定位与标准化（AppleScript：activate + 设 bounds + 取相对坐标）
│   │   ├── clipboard.ts    ④ 剪贴板读写（读消息、备份原剪贴板、结束还原）
│   │   ├── grab.ts        ⑤ 抓取循环（拖选 → 复制 → 读 → 滚动 → 块标记）
│   │   ├── hotkey.ts      ⑥ 紧急停止（macOS 热键 / 信号量）
│   │   └── parse.ts       ⑦ 文本 → 结构化消息（三行一组 → {sender, time, content}）
│   └── types.ts           统一 Message 模型（与 Email 并列的另一种数据源）
└── kb/                     抓到的消息 → 知识库（后续步骤）
```

### 统一 Message 模型

现有的 `Email` 是"邮件"，微信是"聊天"。两者字段不一样，但下游（分词、检索、分类）只关心
**一段文本 + 时间 + 来源**。所以：

```ts
interface Message {
  id: string;          // 内容哈希（同 Email 的做法，天然幂等）
  kind: 'email' | 'chat';
  session: string;     // 邮件=邮箱账号，聊天=会话名"张三/项目群"
  sender: string;
  at: string;          // ISO
  text: string;        // 正文（邮件是纯文本，聊天是消息内容）
  labels: string[];
  meta: Record<string, unknown>;   // 微信特有：轮次、块号、抓取时间
}
```

**关键**：分词、BM25、FTS5、分类管线全部只认 `text` —— 所以微信消息和邮件能被同一套检索命中。
这就是"确定性归代码"的价值：数据源可以换，索引层不用改。

## 五、抓取循环（移植自参考仓库，参数含义写清）

一轮 = 选一块 → 复制 → 读 → 滚。

```
第 N 轮：
  1. 鼠标移到窗口内 (相对坐标) → mouseDown
  2. 缓慢拖到选区另一端（duration 1.8s，慢一点，防界面跳帧漏内容）
  3. 等 3s（等选中内容渲染完成）→ mouseUp
  4. 点「复制」→ 等 1.5s（等剪贴板填充完）
  5. 读剪贴板 → 追加到内存缓冲（带块标记，记下轮次）
  6. 滚轮下滚 SCROLL_STEP 像素 → 等 3.5s（等历史消息加载完）
  重复，直到：
     · 达到最大轮数 / 抓到内容不再变化（到底了）→ 或用户按紧急停止
```

**参数为什么是这些值**（都是参考仓库踩出来的经验值，别乱调）：

| 参数 | 参考值 | 为什么 |
|---|---|---|
| 拖拽时长 | 1.8s | 太快界面来不及渲染，会漏中间的消息 |
| 拖完等待 | 3s | 等选中高亮完成，否则复制到的是旧的 |
| 复制后等待 | 1.5s | 剪贴板是异步填充的 |
| 滚动步长 | 900px | 太大 → 两轮重叠产生大量重复；太小 → 轮数暴增 |
| 滚动后等待 | 3.5s | 等微信把历史消息加载出来，否则会断层 |
| 拖选起点 | 最新一条消息左下角 | |
| 拖选终点 | 聊天框上方中间 | 框住更多底部消息 |

**去重策略**（比参考仓库更严）：
参考仓库用「整行字符串」去重 —— 我们用 `(sender, time, content前32字)` 的哈希做指纹，
因为整行去重在「同一个人同一时间发了两条一样的消息」时会误删。

**增量策略**：
每次抓取记一个「水位」= 最后一条成功解析的消息的 `(time, sender, content前缀)`。
下次抓取时，先滚到底部方向抓最新的（微信聊天按时间正序，最新在最下），
解析后按水位裁掉已处理的部分 → 只处理新增。

**降级与终止**：
- 抓不到内容（剪贴板没变）连续 N 轮 → 认为到底了，结束
- 剪贴板内容与上一轮完全相同 → 说明滚不动了，结束
- 用户按紧急停止 → 立刻结束，**已抓到的内容仍然保留**（参考仓库这点做得好，要保留）
- 抓取前先备份系统剪贴板，结束后还原（礼貌）

## 六、解析器（三行一组 → 结构化）

微信复制出来的文本长这样：

```
张三
2026年11月02日 09:15
你好，那个方案定了没？
```

参考仓库的解析逻辑（`wechat_tidy.py`）：

1. 逐行扫描，用正则 `^(\d{4}年\d{2}月\d{2}日\s+\d{1,2}:\d{2})$` 认时间戳行
2. 时间戳行的**上一行**是发送者、**下一行**是内容 → 三行组成一条消息
3. 跳过分块标记 `----------【第X轮消息块】----------`
4. 去重 → 按时间排序

**我们要加的三点**：
- **多行消息**：微信长消息（多行文本）复制出来是多行 → 不能只取下一行，
  要"一直取到下一个时间戳行之前"。参考仓库没处理这个，是它的已知短板。
- **时间解析**：参考仓库用 `datetime.strptime`，遇到「昨天/星期几」这种相对时间会炸 →
  我们用容错解析，失败的保留原文并标 `at: ''`
- **系统提示行**：微信会插入「以下为新消息」「撤回了一条消息」这类行 → 要识别并单独标记，
  不能当普通消息混进去（否则污染检索）

## 七、隐私与安全

| 风险 | 措施 |
|---|---|
| 剪贴板泄露 | 抓取前备份原剪贴板，结束还原；不写入任何日志 |
| 原始内容落盘 | **不落盘**（沿用邮件那边的规则）：解析完直接进内存/知识库 |
| 抓取时暴露屏幕 | 抓取前提示用户、倒计时 5 秒、期间不切窗口 |
| 误抓敏感会话 | 抓取前让用户明确选择会话（不做全量） |
| 知识库里残留 | 知识库的原文 chunk 是"我们自己选的"，用户可随时删库 |

**一句话**：这个工具的本质是"帮你操作你自己的客户端"，不碰任何账号密码、不碰加密文件。

## 八、验收标准

| 验收项 | 判据 |
|---|---|
| 窗口无关 | 换分辨率 / 移动窗口位置后重抓，结果一致 |
| 不漏不重 | 连续两次抓同一会话，去重后消息数与内容完全一致 |
| 解析正确 | 三行一组能解析出 sender/time/content；多行消息不截断 |
| 增量正确 | 第二次抓取只新增部分，与"全量抓取再裁剪"的结果一致 |
| 可中断 | 任何时刻停止，已抓内容不丢 |
| 不落盘 | 抓取过程中 `find . -newer <起始时间>` 查不到任何新建的数据文件 |

## 九、开发顺序（数字 = 步骤）

1. `capture/types.ts` —— 统一 Message 模型（先把"两种数据源、一个模型"定死）
2. `capture/wechat/parse.ts` —— **纯函数解析器**（最难的部分，先做，可离线测）
3. `capture/wechat/clipboard.ts` —— 剪贴板读写 + 备份还原（macOS 用 `pbcopy`/`pbpaste`）
4. `capture/wechat/window.ts` —— AppleScript 激活 + 标准化窗口 + 相对坐标
5. `capture/wechat/grab.ts` —— 抓取循环（拼装前面几块）
6. `capture/wechat/hotkey.ts` —— 紧急停止
7. `tools/wechat-probe.ts` —— 手动探针（像 imap-probe 那样：跑一次看看抓到了什么）

**为什么先做解析器**：它是纯函数，能用构造的假文本离线测（像 mailbox 那样），
不需要打开微信、不需要任何权限。剩下的都是"和系统打交道"的胶水代码。

## 十、与既有模块的关系

```
微信抓取 ─→ Message ─┐
                      ├─→ tokenize.ts ─→ BM25 / FTS5 ─→ 检索 ─→ qa 问答
邮件抓取 ─→ Email ────┘                      │
                                             ├─→ classify 分类
                                             └─→ digest 晨报
```

- 分词、索引、分类、问答：**完全复用，一行都不用改**（因为 Message 和 Email 对下游只暴露 text）
- 新增的只有 `capture/` 这一层
- 知识库（kb/）两种数据源一起装 —— 这就是当初把 Message/Email 抽象成同一形状的回报

## 十一、已知风险与放弃条件

| 风险 | 什么时候放弃 |
|---|---|
| 微信新版改 UI，坐标失效 | 窗口标准化解决；真失效就改 `window.ts` 的相对定位逻辑 |
| macOS 辅助功能权限拿不到 | 明确报错，让用户去「系统设置→隐私与安全性→辅助功能」授权 |
| 微信 AX 读不到文本 | 退化到剪贴板方案（本来就是主路线） |
| 抓取速度太慢 | 调 SCROLL_STEP / WAIT_AFTER_SCROLL；轮数上限兜底 |
| 消息量太大（几万条） | 一轮几秒 → 上万条要几小时 → 改成"按时间范围分段抓取" |

**放弃条件**：如果 macOS 版微信完全不给辅助功能权限且剪贴板路径也不稳，
就退回**手动导出**（用现成工具产出 tidy.txt，我们的 `parse.ts` 照样能吃）——
解析器是我们自己的资产，不依赖抓取方式。
